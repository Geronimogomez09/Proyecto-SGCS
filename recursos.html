A

Agilidad

Capacidad de adaptarse a cambios durante el desarrollo de software.

Algoritmo

Conjunto ordenado de pasos que permiten resolver un problema o realizar una tarea.

Análisis de requisitos

Proceso de identificar y comprender qué necesita el usuario del sistema.

Automatización de pruebas

Uso de herramientas y scripts para ejecutar pruebas de software automáticamente.

B

Backlog

Lista priorizada de funcionalidades, tareas o mejoras que el equipo puede desarrollar.

Bug

Error que provoca que un programa funcione de manera incorrecta.

C

Calidad de software

Grado en que un programa cumple los requisitos y satisface las necesidades de los usuarios.

Caso de prueba

Conjunto de condiciones, datos y pasos utilizados para comprobar una funcionalidad.

Ciclo de vida del software

Conjunto de etapas por las que pasa un producto desde la concepción hasta su mantenimiento.

Código fuente

Instrucciones escritas por desarrolladores mediante un lenguaje de programación.

D

Depuración

Proceso de encontrar, analizar y corregir errores en el código.

Desarrollo de software

Proceso de diseñar, construir, probar, entregar y mantener aplicaciones informáticas.

Diseño de software

Planificación de la estructura, los componentes y el comportamiento de un sistema.

E

Error

Equivocación humana que puede introducir un defecto y provocar un funcionamiento incorrecto.

Especificación

Descripción de los requisitos, las restricciones y las características que debe cumplir un sistema.

Estándar

Documento de referencia con criterios, requisitos o recomendaciones acordados para un ámbito determinado.

F

Framework

Estructura de herramientas, bibliotecas y convenciones que facilita la construcción de aplicaciones.

G

Gestión de calidad

Actividades coordinadas para planificar, controlar, asegurar y mejorar la calidad del software.

H

Historia de usuario

Descripción breve de una necesidad desde el punto de vista de quien utilizará el producto.

I

Incidencia

Situación detectada que requiere análisis, seguimiento o una acción correctiva.

Integración continua

Práctica de incorporar cambios al código frecuentemente y comprobarlos mediante pruebas automatizadas.

J

JavaScript

Lenguaje de programación utilizado para añadir comportamiento e interactividad a páginas web.

K

Kanban

Método visual para organizar tareas, limitar el trabajo en curso y observar el flujo de un equipo.

L

Lean Software Development

Enfoque que busca reducir actividades que no aportan valor y mejorar el flujo de entrega.

M

Mantenimiento

Modificación del software para corregir defectos, mejorar su funcionamiento o adaptarlo a nuevas necesidades.

Modelo XP

Extreme Programming, enfoque ágil que promueve programación en parejas, pruebas frecuentes y mejora continua.

N

Normalización

Proceso de organizar datos para reducir redundancias y mejorar su consistencia, especialmente en bases de datos.

O

Open Source

Software cuyo código fuente está disponible para consultar y, según su licencia, modificar y distribuir.

P

Prueba de software

Evaluación de un sistema para comprobar su comportamiento y detectar defectos.

Prueba de regresión

Prueba que verifica que los cambios recientes no hayan afectado funcionalidades existentes.

Q

QA (Quality Assurance)

Aseguramiento de la calidad mediante procesos y actividades dirigidos a prevenir problemas y mejorar el trabajo.

R

Requisito

Necesidad, capacidad o condición que un sistema debe cumplir.

Revisión de código

Examen del código por otra persona o mediante herramientas para detectar problemas y mejorar su claridad.

S

Scrum

Marco de trabajo que organiza el desarrollo en ciclos llamados sprints y promueve la inspección y adaptación.

Seguridad del software

Capacidad de proteger la información y el funcionamiento del sistema frente a amenazas y usos indebidos.

Software

Programas, datos y elementos relacionados que permiten a un sistema informático realizar tareas.

T

Testing

Actividad de probar un programa para comprobar su comportamiento y encontrar defectos.

Trazabilidad

Capacidad de relacionar requisitos con diseños, código, pruebas y resultados para seguir su cumplimiento.

U

Usabilidad

Grado en que las personas pueden utilizar un sistema con eficacia, eficiencia y satisfacción.

V

Validación

Comprobación de que el software satisface las necesidades y el uso esperado por las personas usuarias.

Verificación

Comprobación de que el producto cumple las especificaciones y requisitos establecidos.

Versión

Estado identificable de un software que corresponde a una entrega o conjunto de cambios.

W

Waterfall

Modelo de desarrollo secuencial en el que las etapas se realizan principalmente una después de otra.

X

XP (Extreme Programming)

Enfoque ágil que prioriza la calidad del código, la colaboración, las pruebas y las entregas frecuentes.

Y

YAGNI

Principio que propone no implementar una funcionalidad hasta que realmente sea necesaria.

Z

Zero-day

Vulnerabilidad que se conoce cuando todavía no existe una corrección ampliamente disponible o que puede explotarse antes de que haya un parche.

Preguntas frecuentes

Resolvé tus dudas

Encontrá explicaciones sobre calidad, aseguramiento, pruebas y buenas prácticas de desarrollo.

Abrí un tema y seleccioná una pregunta. Se mantiene abierto un solo tema y una sola respuesta a la vez.

Debe cumplir sus requisitos y satisfacer las necesidades de sus usuarios. Según el contexto, se evalúan características como adecuación funcional, rendimiento, compatibilidad, facilidad de uso, fiabilidad, seguridad, mantenibilidad y flexibilidad para adaptarse.

Se define qué atributos importan y se seleccionan medidas verificables. Por ejemplo: porcentaje de pruebas superadas, defectos detectados, tiempos de respuesta, disponibilidad, incidencias en producción y resultados de pruebas de usabilidad. Una métrica aislada no representa toda la calidad.

La calidad del producto se refiere a las propiedades del software entregado y a cómo cumple las necesidades. La calidad del proceso se refiere a las actividades y prácticas usadas para construirlo, revisarlo, probarlo y mantenerlo. Un proceso sólido ayuda, pero no garantiza por sí solo un buen producto.

Proporciona un modelo de calidad de producto que permite describir, especificar y evaluar propiedades del software y de sistemas TIC. Ayuda a elegir características y subcaracterísticas pertinentes para los objetivos del proyecto.

Consultar ISO/IEC 25010 en ISO

El aseguramiento de calidad (QA) se centra en los procesos y en prevenir defectos; el control de calidad evalúa los productos o entregables para identificar problemas. Las pruebas son una de las actividades que pueden formar parte del control de calidad.

Ayuda a detectar defectos antes de integrar cambios, mejora la legibilidad, facilita compartir conocimiento y permite revisar seguridad y mantenibilidad. No reemplaza las pruebas: ambas prácticas se complementan.

Entre otras, pruebas unitarias, de integración, de sistema y de aceptación. También pueden ser necesarias pruebas no funcionales, como rendimiento, seguridad, accesibilidad y usabilidad. La selección depende de los riesgos y requisitos del producto.

Conviene considerar la automatización cuando una prueba se repite, tiene resultados comprobables y aporta valor en cada cambio, como las pruebas de regresión. Las comprobaciones exploratorias o muy subjetivas pueden requerir intervención humana.

Evaluá la estabilidad de requisitos, el riesgo, el tamaño y la experiencia del equipo, la disponibilidad de usuarios, la necesidad de entregas, la trazabilidad y las obligaciones de calidad. No existe un modelo universalmente mejor: la elección depende de las restricciones del contexto.

Scrum organiza el trabajo en sprints y define responsabilidades, eventos y artefactos. Kanban se centra en visualizar y gestionar el flujo continuo, limitar el trabajo en curso y mejorar el tiempo de entrega. Pueden compartir algunas prácticas, pero no son lo mismo.

Puede encajar cuando los requisitos son relativamente estables, las etapas y entregables pueden definirse con anticipación y existen aprobaciones formales. Si los cambios son frecuentes o la solución todavía es incierta, conviene revisar los riesgos de una secuencia rígida.

Significa que se puede comprender, corregir, adaptar y ampliar con un esfuerzo razonable. Un diseño claro, pruebas confiables, documentación útil y componentes bien separados ayudan a mantenerlo.

La documentación útil explica decisiones, requisitos, instalación, arquitectura, interfaces y procedimientos que no resultan evidentes al leer el código. Debe mantenerse actualizada y enfocarse en lo que realmente necesitan los usuarios y el equipo.

Es el costo futuro asociado a decisiones técnicas que facilitan avanzar ahora pero complican cambios posteriores. No toda deuda es necesariamente mala; conviene hacerla visible, comprender sus consecuencias y decidir cuándo reducirla.

Permite registrar cambios, comparar versiones, colaborar, revisar propuestas y recuperar estados anteriores. Herramientas como Git ayudan a mantener un historial y a organizar el trabajo entre ramas.

Es la práctica de integrar cambios pequeños con frecuencia y ejecutar comprobaciones automatizadas para detectar problemas temprano. Funciona mejor con pruebas confiables, revisiones y un proceso de construcción reproducible.

Depende del contexto: defectos por versión, pruebas superadas, tiempos de resolución, disponibilidad, tiempos de respuesta, incidencias posteriores a la entrega o resultados de usabilidad. Las métricas deben ayudar a decidir y no convertirse en objetivos aislados que se puedan manipular.

Se pueden combinar revisiones entre personas, analizadores estáticos, linters, pruebas automatizadas y escáneres de seguridad. Ninguna herramienta detecta todos los problemas; conviene elegirlas según el lenguaje, el riesgo y el flujo del equipo.

Desde el análisis de requisitos y el diseño hasta el desarrollo, las pruebas, el despliegue y el mantenimiento. Identificar amenazas temprano y revisar dependencias, permisos, datos y configuración reduce el riesgo de descubrir vulnerabilidades cuando el sistema ya está en producción.
